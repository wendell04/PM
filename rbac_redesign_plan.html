Personalize Me Prints · Authorization Redesign

Who Can Do What

A plan to split system authority from business authority, replace the on/off permission toggles with real actions, and make the backend the boundary it currently only pretends to be.

Stack Laravel · MongoDB · Sanctum · Next.js Status Proposal — nothing implemented Scope RBAC only Verified against working tree
01

What exists today

The bones are sound: users carry a single role string, and staff roles resolve their permissions from a shared document. Change the role, and everyone on it changes with it — exactly the model we want. The problem is enforcement, not shape.

  • Auth — Sanctum bearer tokens; every account is a User with one role string.
  • Roles — built-ins admin, owner, customer; staff roles are docs in the role_permissions collection, created at runtime through the admin UI (no seeder).
  • Permissions — 19 module-level on/off booleans per role (orders, inventory, userManagement…).
  • Enforcement — a coarse gate (IsAdminMiddleware) plus a fine gate (hasPermission()) in ~17 of 35 controllers, and a frontend can(permKey) that hides sidebar items.
  • The bypass — in_array($role, ['admin','owner']) returns full access in five places: isAdmin(), hasPermission(), hasRole(), myPermissions(), and the frontend can().
The core finding

admin and owner are, today, the same omnipotent role. There is no system-vs-business distinction to protect, and no superAdmin at all. Everything below builds that distinction.

02

What's broken

Four gaps, ordered by how much damage each allows. The first is a live vulnerability, not a design preference.

Critical

The toggles are frontend-only for ~15 modules

The coarse gate admits any provisioned staff role into /admin/*. Only ~17 controllers then call hasPermission(). Missing entirely: PaymentController, BannerController, FlashSaleController, VoucherController, SettingsController, SiteContentController. A production staffer who knows the URL can call payments or catalog endpoints directly with every toggle OFF. This is the "don't trust the frontend" hole, and it is real.

Critical

No system / business separation

Both admin and owner bypass everything. The Owner can currently reach system-level surfaces (editing any role) that should belong only to the developers.

High

Privilege-escalation seam

getStaffRoles() returns every role in the collection. The moment a powerful role is seeded there, it becomes assignable by anyone holding userManagement — including assigning a role above one's own. Nothing checks the actor's level against the target's.

High

orders is a single toggle

Production needs to view an order and update its production status without seeing price, payment, or refunds. One boolean can't express that — the model itself is too coarse for the business rule.

Two smaller ones: staff/role management is locked to admin/owner at the route (so a business Administrator can't manage staff even when granted it), and the audit log has a delete path where it should be append-only.

The overhaul, done safely

You asked for a real overhaul that doesn't ruin the code. The safe path is to keep the storage shape and migrate the values in one reversible pass — old keys map to clean ones, three new roles are added, and every user.role is rewritten in the same migration.

Don't lock yourselves out

Ship the superAdmin split with an env-flagged break-glass account, off by default, every request it serves logged. A misconfigured grid must never be able to shut the developers out of their own system.

04

Action-based permissions

Replace { orders: true } with { "orders.view": true, "orders.updateStatus": true }. Keys are module.action; the storage stays a flat object of booleans, so the collection shape and the merge-with-defaults logic survive. Checks become hasPermission($req, "payments.refund").

  • orderRequestsview · create · edit · delete · approve
  • ordersview · create · edit · delete · updateStatus
  • jobOrdersview · create · edit · delete · updateStatus
  • posview · sell · void
  • inventoryview · create · edit · delete
  • vendorsview · create · edit · delete
  • badOrdersview · create · edit · delete
  • salesview · export
  • reportsview · export
  • products / banners / flashSales / vouchersview · create · edit · delete
  • payments newview · create · edit · delete · confirm · refund
  • auditLogsview (append-only — no delete)
  • usersview · create · edit · disable · delete · assignRole
  • rolesview · create · edit · delete · assignPermissions
The Production-Staff rule, concretely

Two pieces solve it: grant orders.view + orders.updateStatus but not orders.edit; and have the Orders API strip price / payment / refund fields from the response for any role lacking payments.view. Hiding a column in the UI is not enough — the field must never leave the server.

06

Authorization flow

One centralized path, applied as a permission:<key> route middleware on every /admin/* route. No controller decides its own gate; a route with no key is a bug the router refuses to serve.

1auth:sanctum — valid token, or 401
2Super Admin? → allow everything (the only true bypass)
3Owner + the route's key is a business key? → allow
4Everyone (Owner on system keys included) → hasPermission(role, key)
5Granted → allow   ·   else → 403

Sensitive write paths add a second guard beyond the route key: role-assignment endpoints reject any target of superAdmin, and any target role ranked above the actor's own — enforced in the controller because it depends on the request body, not just the route.

07

Data & backward compatibility

One idempotent migration, safe to re-run, reversible. No collection is dropped; no user is stranded.

  • Expand permissions — for every role doc, each old module boolean becomes its action set: true → all actions true, false → all false. New defaults merge in as false (least privilege), so untouched roles simply gain unset actions.
  • Sensitive actions default closed — *.delete, payments.refund, users.assignRole, roles.assignPermissions migrate to false even from an old true, so no one silently inherits a dangerous new right.
  • Rewrite role keys — update user.role and the role _id/role field together in one pass; preserve existing staff assignments by mapping, never deleting.
  • Seed the new roles — administrator, manager, financeStaff created with the matrix defaults if absent.
  • Drive the frontend from the API — replace the hard-coded STAFF_ROLES list and role labels with the roles endpoint, so new roles need no frontend edit.
08

Build order

Each phase is shippable and reversible on its own. The sequence matters: step 2 is what makes the toggles real, and it must land before anyone relies on them.

  1. security

    Split Super Admin from Owner

    Add superAdmin to the bypass in all five checks; demote Owner to business scope. Migrate current admin users; add the env-flagged break-glass account in the same change.

  2. security

    Centralize enforcement

    Introduce permission:<key> route middleware and apply it to every /admin/* route. This structurally closes the ~15 unguarded controllers — no per-controller archaeology.

  3. safety

    Close the escalation seam

    Exclude protected roles from assignable lists; reject assigning superAdmin or any role above the actor's own; block editing protected roles in the permission UI and API.

  4. data

    Migrate to action-based permissions

    Run the expand-and-rename migration; refactor hasPermission() to dotted keys; seed the three new roles.

  5. safety

    Harden orders for Production

    Add the payments key; strip financial fields from the Orders response for roles without payments.view.

  6. audit

    Audit + append-only

    Log role-assigned, role/permission-changed, user created/disabled/deleted. Remove the audit-log delete path for every role.

  7. ui

    Frontend follows

    Move to action-aware can(), drive roles/labels from the API, mark protected roles read-only, and reflect the new matrix in the Permissions screen.
